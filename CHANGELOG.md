### Added

- **SAM parameter `CampaignResponseUpdateIntervalMinutes`** (default 30) for `campaignResponse.updateIntervalMinutes`, which until now could only be set by hand on the function.
- **A project logo** (`docs/assets/phishy-logo.svg`), shown at the top of the README.
- **Security-team members who may issue commands** (`notification.securityTeamMembers` / `SECURITY_TEAM_MEMBERS`, SAM `SecurityTeamMembers`; default empty). When `SECURITY_TEAM_DISTRIBUTION` is a list address, a team member replying from their own mailbox was not on it and could not record a verdict or approve an action. Addresses listed here may now do both, with the same checks as the distribution addresses: exact address match and SES SPF or DKIM `PASS`. Members are never sent anything: report Cc, incident emails and alerts still go only to the distribution, and the answer to a command goes to its sender. A member address outside `email.safeDomains` is ignored, with a startup warning that gives only the count. The combined set (`securityTeamCommandSenders`) is used for command and approval authorization and for recognizing the team's own incident-thread replies (`own.report.ts`).
- **Microsoft Graph foundation** (`src/services/graph/`; `graph.enabled` / `PHISHY_GRAPH_ENABLED`, off by default; changes nothing on its own).
  - App-only authentication with a certificate-signed JWT assertion (PS256, `x5t#S256`; no client secret, no new dependency), an in-memory token cache with one shared in-flight request. Settings `PHISHY_GRAPH_TENANT_ID`, `PHISHY_GRAPH_READ_CLIENT_ID`, `PHISHY_GRAPH_READ_CERTIFICATE` (Secrets Manager ARN or inline PEM).
  - A constrained client: fixed `https://graph.microsoft.com/v1.0` base URL; `graphPath` / `odataFilter` tagged templates (plus `kqlSearch`, `odataSeconds`, single-property `$expand`) as the only way data enters a request; `@odata.nextLink` followed only on the Graph origin; caller-capped paging (`getPaged`, and `getPage` with an opaque cursor); an optional caller `signal`; bounded `Retry-After`, timeouts and response sizes; typed errors that never carry tokens, key material or bodies.
  - A typed, GET-only operations library (`mail.operations.ts`, `trace.operations.ts`, `directory.operations.ts`): messages by Internet message ID or sender + window, search, Internet headers, MIME with a size cap, last verb, message trace by message ID, sender + subject, recipient or time window (5000 `$top` cap, rows verified against the requested address: the service silently ignores `endswith` / `contains` address predicates), users, subscribed-SKU capabilities. `MessageSummary` includes `isRead`.
  - **`npm run graph:probe`** (`phishy-graph-probe`): a local, read-only check of which of those calls work in your tenant, with which permissions and licences. Identifiers hashed unless `--show-identifiers`; `--json`. See `docs/GRAPH_PROBE.md`.
  - Entra app-registration, certificate and Exchange "RBAC for Applications" guidance in `docs/CONFIGURATION.md`.
- **Graph broker** (`graph.mode: broker` / `PHISHY_GRAPH_MODE=broker` with `PHISHY_GRAPH_BROKER_FUNCTION`; `direct` stays the default): Graph requests move to a second Lambda function so the function that parses hostile email holds no Graph credential and needs no internet route.
  - The broker (`src/handlers/graph.broker.handler.ts`, entry `src/graph-broker.ts`, handler `graph-broker.handler`) runs outside the VPC, holds the read certificate, never parses a raw email, and accepts only a strict, versioned request for one of four typed operations: `original_message_lookup`, `sender_history_lookup`, `blast_radius_lookup`, `fanout_scan`. No path, URL, filter or passthrough; anything else is refused; it never throws and logs counts and outcomes only. It loads only `graph.*` and the log level, and refuses an operation whose feature flag is off in its own configuration.
  - In broker mode the main function drops any `graph.tenantId` / `graph.read.*`, builds no Graph client, and calls the broker through Lambda `Invoke` (`graph.gateway.ts`). Answers are treated as hostile: size-checked, schema-validated per operation and re-bounded (500 headers, 20 burst IPs, 100 listed recipients). Any broker failure is the feature's ordinary Graph failure. Rate limits and caches live in the broker. New dependency `@aws-sdk/client-lambda`; metrics `GraphBrokerCalls`, `GraphBrokerCallDurationMs` (`Operation`, `Outcome`).
  - SAM: `GraphEnabled` (default `false`), `GraphTenantId`, `GraphReadClientId`, `GraphCertificateSecretArn`, `GraphOriginalFetchEnabled`, `GraphBlastRadiusEnabled`, `GraphSenderHistoryEnabled`, `GraphBrokerReservedConcurrency` (default 5; 0 reserves nothing). With Graph enabled the stack adds `GraphBrokerFunction` (no VPC, no trigger, 512 MB, 180 s), its own least-privilege role and log group, broker mode and `lambda:InvokeFunction` on the main function (no tenant ID, client ID, certificate or secret access), and a Lambda interface endpoint when the main function is in a VPC with `CreateVpcEndpoints=true`. A rule rejects `GraphEnabled=true` without the three required values; with Graph disabled the template creates what it did before. See `AWS.md`.
- **Original-message lookup** (`graph.originalFetch.enabled` / `PHISHY_GRAPH_ORIGINAL_FETCH_ENABLED`, needs Graph and `Mail.Read` on reporters' mailboxes): before analysis, the original of a forwarded email is found in the reporter's own mailbox and its real Internet headers (`Authentication-Results`, `Received`, `Return-Path`, `Reply-To`, `Message-ID`) are read.
  - Only the reporter's mailbox, only when the report's `From` is the safe-domain forwarder and SES reports SPF or DKIM `PASS`. Matched by claimed sender, sent-time window and exact subject (escaped `$filter` literals) across the mailbox and Recoverable Items; used only when exactly one message matches and passes a re-check in code.
  - The retrieval is a `VERIFIED` fact; every header stays `CLAIMED` in its own nonce fence, in stored order, bounded adversarially (per-name first+last quotas, head+tail values, priority budget), every cut disclosed.
  - A plus-address or alias Graph does not know as a mailbox ends `not_found` / `mailbox_not_found`; a `+tag` address is retried once without the tag (same domain, safe-domain checked again).
  - When the retrieved original's sender domain differs from the forwarded one, the anchor checks are redone against it.
  - No match, several matches, any error or the 8-second budget leave analysis unchanged. Metrics `OriginalFetchCount` (`Outcome`: `found` / `not_found` / `ambiguous` / `error` / `skipped`), `OriginalFetchDurationMs`.
- **Sender-relationship check** (`graph.senderHistory.enabled` / `PHISHY_GRAPH_SENDER_HISTORY_ENABLED`, needs Graph and `ExchangeMessageTrace.Read.All`): catches a known external contact whose mailbox has been taken over.
  - Before analysis, code reads message trace for the claimed sender and computes counts: history and distinct recipients over a lookback (default 30 days, max 90), two-way contact, a burst window, recipients new to the sender, the widest single subject in the burst, whether the burst's sending IPs were seen before. Classification `no_history` / `limited_history` / `established` / `established_with_anomalous_fanout`, to the model as a VERIFIED block of numbers, to risk fusion and to the report.
  - `established_with_anomalous_fanout` requires two-way contact and one subject reaching at least `fanoutMinRecipients` (default 15) distinct recipients, `fanoutMultiplier` (3) times the history's reach, most of them new. Known limit: a takeover reaching fewer recipients is not flagged by this rule.
  - **A relationship never lowers risk**: only anomalous fan-out acts (one reason, a floor of 35).
  - The detail follows the audience: counts in the combined report; nothing but one sentence on anomalous fan-out in the reporter's own copy; sending IPs (at most 20, never in the prompt) only in an email to the security team alone.
  - Bounded: 6 trace requests at the defaults under an 8 s deadline, capped rows reported as "at least N", a per-instance allowance of 60 requests per 5 minutes and a 5-minute cache. A 403 is retried up to 3 times (message trace answers 403 intermittently while its service principal propagates); `forbidden` with a 5-minute pause only when nothing succeeded. Rows that name a different address discard the lookup (`filter_not_applied`). Recipients are counted per message, recipient and time (trace gives all recipients of one message the same row `id`). Any failure leaves analysis unchanged; nothing is persisted.
  - Metrics `SenderHistoryLookups`, `SenderHistoryDurationMs`, `SenderHistoryAnomalousFanout`, `SenderHistoryTruncated`, `SenderHistoryForbiddenRetries`, `SenderHistoryFilterMismatches` (`Outcome`).
- **Blast radius** (`graph.blastRadius.enabled` / `PHISHY_GRAPH_BLAST_RADIUS_ENABLED`, needs Graph): after a malicious verdict, who else in the organization received the message and whether they read, replied to or forwarded it, for the **security team's copy only**.
  - The reporter's report goes first, without the security team in Cc; the security team then gets its own copy with the section (or a one-line note on failure); a reporter on the security team gets only that copy; a failed security copy emits `SecurityCopySendFailures`. A malicious Report-button report gets one email to the security team, with the section.
  - Code-driven and read-only, never shown to the model, nothing persisted: by Message-ID or claimed sender + subject + window; message trace first (each recipient's mailbox read by the Message-ID trace recorded for them, distribution-list expansion rows left out, failed deliveries listed as not delivered), falling back to a per-mailbox search of licensed user mailboxes including Recoverable Items.
  - Bounded by `PHISHY_GRAPH_BLAST_RADIUS_TIME_BUDGET_MS` (45000) and `PHISHY_GRAPH_BLAST_RADIUS_MAX_MAILBOXES` (2000); partial coverage always stated. Per mailbox it also carries, never rendered, the directory ID, up to 5 matching Graph message IDs and the arrival time, for response actions. `BlastRadius*` metrics.
- **Scheduled fan-out scan** (`graph.fanoutScan.enabled` / `PHISHY_GRAPH_FANOUT_SCAN_ENABLED`, needs Graph, `ExchangeMessageTrace.Read.All`, the intelligence database and **migration 005**): Phishy's first proactive check, with **no AI model**.
  - Every few minutes it reads recent inbound mail flow from message trace and flags an established external contact suddenly sending one subject to many internal people (the sender-relationship rule, run before anyone reports). A schedule invokes the main function with exactly `{"phishyScheduledTask": "graph_fanout_scan", "version": 1}` (anything else carrying that key is refused; email events never reach the scheduled path).
  - Bounded and disclosed: page and candidate caps, a time budget, and a message-trace allowance shared by all scans (`requestAllowancePer5Min`, default 20, tracked in the database; each broker instance also caps scans at 40). Every request, history pages included, is counted before it is made; a page the allowance has no room for is not requested, the scan is `incomplete`, and a window the allowance left unread is read again by the next scan. One scan at a time (database lock with a lease), overlapping windows, one alert per sender-and-subject wave, an update only on material growth.
  - The alert (security team only, code-written subject, stable `FANOUT-…` reference) says it is a behaviour-based flag, what was seen, delivery states, what to check and the benign explanations, with blast radius when on and up to 100 recipients. **With campaign response on, a flagged wave opens an incident and the incident email replaces the alert** (approval-only; growth is a threaded update; the plain alert is still sent when no incident email went out). Replying to a plain alert triggers nothing; `FanoutScanStore.findWave` is the seam.
  - Settings `overlapMinutes`, `maxWindowMinutes`, `maxPages`, `maxCandidates`, `requestAllowancePer5Min`, `budgetMs`, `dedupeHours`; metrics `FanoutScans`, `FanoutScanDurationMs`, `FanoutScanRowsScanned`, `FanoutScanCandidates`, `FanoutScanFlags`, `FanoutScanAlertsSent`, `FanoutScanIncomplete`, `FanoutScanTraceRequests` (`Outcome`).
  - SAM: `GraphFanoutScanEnabled` (default `false`) and `GraphFanoutScanIntervalMinutes` (default 5, 2-60) add an EventBridge rule (`FanoutScanSchedule`, no retries) and a scoped invoke permission; a rule rejects the scan without `GraphEnabled` or `IntelligenceDbSecretArn`.
- **Campaign response** (`campaignResponse.enabled` / `PHISHY_CAMPAIGN_RESPONSE_ENABLED`; needs campaign alerts, the intelligence database and **migration 006**; approvals need the command channel). A campaign becomes an incident.
  - **Triggers:** the report-count threshold, or the **reach trigger** (`reachThreshold`, default 5, `0` off): with blast radius on, the first malicious report (phishing, BEC or malware delivery) whose lookup listed at least that many delivered recipients besides the reporters; or the **fan-out scan** (zero reports, approval-only). One incident per campaign signature; later reports join it.
  - **Incident email** to the security team, built for a decision: what changed (in an update), a headline saying what is waiting and why, the verdict, reach as number tiles, only what Phishy actually did, proposed actions each with its exact reply line after "Reply with this line:", a separate "If this is not phishing" option, then the attack, timeline and recipients as evidence. Subject `[Phishy incident <reference>] Active phishing campaign` (the lure's subject is in the body only). Updates thread in the same conversation (`SESNotifier.sendThreadedEmail`, `SendRawEmail`), at most one per `updateIntervalMinutes`.
  - **Targeted warning** (`audience: recipients` or `both`) to the people blast radius found, one email each, with the organization's `alreadyClickedInstructions`; waits for approval by default (`employeeWarning: approve`; `auto`, `off`). The distribution broadcast keeps its behaviour (`distributionWarning: auto`). Addresses must be on a safe domain (checked twice), capped by `maxWarningsPerCampaign` (distinct employees emailed), nobody whose copy was not delivered, reporters never; attack text is defanged so no link is clickable.
  - **Automatic actions need two reporters:** an `auto` action is proposed for approval until two different people have reported the campaign, then runs once; an auto warning is sent only by the invocation that moved it to `approved`.
  - **Removal** ("remove remaining copies") is proposed with exact Graph message IDs per mailbox, capped by `maxRemovalMailboxes` / `maxRemovalMessages`, always for approval; approving it runs a **dry run** by default that reports what it would remove, or, with the mailbox write tier (below), moves the copies to Deleted Items.
  - **Removal notice:** one email to each person whose copy a live removal actually moved to Deleted Items, under the warning's rules. Sent only when a removal executor returns `dryRun: false` with a `removed` list, so never after a dry run. There is no thank-you email to reporters; results written by pre-release builds that list `thanked` addresses are still read as already contacted.
  - **Approvals** over the command channel: `APPROVE WARNING <ref>` / `APPROVE REMOVAL <ref>`, same authentication as every command, read only from the reply's own new text and never by the model, unguessable per-action references, idempotent, expiring after `approvalTtlHours`. A reply whose own text is exactly `APPROVE WARNING` approves the one warning the incident email it answers proposed (matched by `In-Reply-To`; audit event `incident_email_sent`); removal always needs its reference. A `false positive` reply also closes the incident and cancels its actions. A reply whose subject contains `[Phishy incident ` is never analyzed as a report.
  - `migrations/006_campaign_response.sql`: `campaign_incidents`, `response_actions`, append-only `response_action_audit`. New settings `audience`, `employeeWarning`, `distributionWarning`, `approvalTtlHours`, `maxWarningsPerCampaign`, `maxRemovalMailboxes`, `maxRemovalMessages`, `updateIntervalMinutes`, `reachThreshold`, `alreadyClickedInstructions`, `timeZone`. Metrics `CampaignIncidentsOpened` (`Trigger`), `CampaignIncidentUpdates`, `CampaignWarningsSent`, `CampaignRemovalNoticesSent`, `CampaignWarningsSkipped`, `CampaignWarningSendFailures`, `ResponseActionsProposed`, `ResponseActionApprovals`, `ResponseActionApprovalsRejected`, `ResponseActionsExpired`, `ResponseActionsDryRun`.
  - SAM: `CampaignResponseEnabled`, `CampaignResponseAudience`, `CampaignResponseEmployeeWarning`, `CampaignResponseReachThreshold`; with campaign response on, `CampaignAlertDistribution` may be empty.
- **Mailbox write tier** (live campaign removal; off by default at every level): an approved removal can move the approved copies to each mailbox's Deleted Items. Nothing is permanently deleted.
  - **A third function, the Graph write broker** (`src/handlers/graph.write.broker.handler.ts`, entry `src/graph-write-broker.ts`, handler `graph-write-broker.handler`; code in `src/services/graph-write/`), with its own Entra app registration (`Mail.ReadWrite`, application) and certificate. The main function and the read broker never receive the write client ID or secret: their schemas have no place for it (a `graph.write` key is dropped; setting the write variables on the main function logs a warning), and only the write broker's role can read the write secret. It reads its configuration from its own environment only (`loadGraphWriteBrokerConfig`), never the shared S3 file: `PHISHY_GRAPH_WRITE_ENABLED` (its kill switch, default `false`: every request refused `write_disabled`), `PHISHY_GRAPH_TENANT_ID`, `PHISHY_GRAPH_WRITE_CLIENT_ID`, `PHISHY_GRAPH_WRITE_CERTIFICATE`, and `PHISHY_GRAPH_WRITE_ALLOWED_MAILBOX_IDS` (when set, every other mailbox is refused `not_allowed`; set but listing nothing, or not GUIDs, refuses everything as `misconfigured`). It refuses to start if its environment names the read app's client ID or certificate as its own.
  - **Live only for copies that match an anchor** (`src/services/response/removal.eligibility.ts`). Blast radius matches copies by the forward's text, which a hostile email can steer (a reused Message-ID, or a forwarded-header block planted in its body: the parser takes the first block of the first marker type it finds, so a Gmail-style block in the body beats an Outlook reporter's own block; that precedence is unchanged, and live removal does not rely on it). A live removal is proposed only for an incident with reports, a malicious verdict and an anchor: Exchange's stored copy of the original the original-message lookup found in the reporter's mailbox (`retrievedOriginal.identity`: Graph ID, Internet Message-ID, From address, subject; received time), whose Internet Message-ID equals the report's own top-level `In-Reply-To` (a single ID) or, without one, the last `References` entry (never body text or an attached message's headers), whose subject agrees with the report's own Subject (`RE:`/`FW:`/`Fwd:` removed, `subjectGroupKey`), which a Message-ID search of the reporter's mailbox (normal store and Recoverable Items, made during the original-message lookup within its budget; `identity.sameMessageIdCount`) finds exactly once, which is also the only copy with that ID in the reporter's blast-radius row at index 0 with agreeing stored values, marked forwarded, with a non-empty normalized subject. The lookup that locates the candidate is still keyed on the forward's claims; only these facts bind it. Rejection words: `report_button`, `no_original`, `incomplete_identity`, `not_the_forwarded_message`, `uniqueness_unknown`, `ambiguous_message_id`, `no_blast_radius`, `reporter_copy_not_found`, `reporter_copy_differs`, `not_forwarded_by_reporter` (logged at debug). The first anchor is write-once: creation is `ON CONFLICT DO NOTHING` (the loser joins as an update) and the store's `UPDATE` keeps a stored anchor in one statement. CONFIGURATION.md has a "before turning live removal on" checklist. One eligibility rule, with no setting that loosens it: a copy is eligible only with the anchor's own Internet Message-ID, its From address and exactly its normalized subject (`subjectGroupKey`, compared as SHA-256; never `contains`), arriving within `campaignResponse.removal.sameMessageSpreadMinutes` (default 60) of it; missing data never matches. (A message-trace size band was tried before release and dropped: real copies of one campaign differ in trace size by several percent; pre-release `sizeTolerancePercent` / `windowHours` settings are ignored with a warning, and a stored scope that admitted copies on size never sends them.) Other matched copies stay in the reach (warnings unchanged) and are reported as "not provably the same email: not included". Without an anchor the removal is a dry run and the proposal says why. The proposal states its basis (copies and mailboxes, all with the reported copy's Internet Message-ID; sender; exact subject; arrival span; excluded copies; mailboxes that cannot be checked; the residual risk) and never says a copy "is" the reported email. New setting `PHISHY_CAMPAIGN_RESPONSE_REMOVAL_SAME_MESSAGE_SPREAD_MINUTES`.
  - **The mode is bound to the proposal**: a live scope carries `mode: 'live'`, inside the scope hash. A dry-run proposal always runs as a dry run, a live one runs as a dry run if the deployment is no longer live, and the reply says which; a scope that was dry-run can be proposed again live.
  - **One typed operation**, `remove_messages` (protocol version 2, strict Zod at both ends): per mailbox, `messages: [{ messageId, expectedInternetMessageId, expectedSenderAddress, expectedSubjectSha256, receivedFrom, receivedTo }]` (pairs, not sets; no email text crosses), at most 50 mailboxes, 5 messages each and 100 per call, a 1-80 s budget, 4 mailboxes at a time. Each message is re-read by ID (`$select=internetMessageId,parentFolderId,from,subject,receivedDateTime`) and is `not_found`, `mismatch` (any expected value not met: never moved), `already_deleted`, `moved`, `error` (fixed reason words, never Graph text) or `not_attempted` (time, throttling or authentication stopped the call). Never throws; logs the action ID and counts only.
  - **Its own three-request client** (`GraphWriteClient`, not `GraphClient`): GET the message, GET `mailFolders/deleteditems`, POST `messages/{id}/move` with `destinationId: "deleteditems"`, and nothing else. `429`/`503` honoured with `Retry-After` within the deadline; a move is never repeated after a timeout or `5xx` (`move_unconfirmed`). Build tests fail if a move, delete, `PATCH`, `PUT` or send (single- or double-quoted) appears outside `src/services/graph-write/`, if anything calls the read client's `postJson`, if the main function's or read broker's bundle contains the write client or operation, or if the write broker's bundle contains the read operations, the email parser or the database driver.
  - **The live executor** (`LiveRemovalExecutor`), selected only with `campaignResponse.removal.mode: live` (`PHISHY_CAMPAIGN_RESPONSE_REMOVAL_MODE`) and `campaignResponse.removal.writeBrokerFunctionName` (`PHISHY_GRAPH_WRITE_BROKER_FUNCTION`); `live` without a valid name runs the dry run and logs why. It sends exactly the approved scope after the existing re-check (never wider; copies new since approval are not included, and those of the same email are counted), batches within the bounds while time allows, and waits 10 s beyond each call's budget so a cold write broker still answers. Refusals before any request, Lambda throttling and invoke errors that stop the function from running (`AccessDeniedException`, `ResourceNotFoundException`, `InvalidParameterValueException`, …) are `not_attempted`; timeouts, crashes, `internal_error` and unknown invoke errors are `unknown`, nobody is notified for them, and the approver is told which mailboxes and how to check. It returns `dryRun: false`, a summary by outcome, `removalOutcome` (recorded in the `action_executed` audit row) and `removed` (moved copies only, which is what sends the removal notices). The real result is persisted first; a failure to record it is logged with the counts and the approver still gets the real outcome. Approval is unchanged: the exact `APPROVE REMOVAL <ref>` line; a removal is never automatic. A removal that fully completed is not proposed again with the same scope. An approved removal stuck without a result no longer makes anyone count as already notified.
  - Blast radius now records, per copy, `copyDetails` (Internet Message-ID, From address, subject SHA-256, arrival time; a pre-release broker's per-copy `size` is accepted and dropped), and the original-message lookup records the found message's stored `identity`; both are carried by the read broker's protocol (deploy the main function first, or together: a new read broker with an old main function is answered `malformed`). Copy-detail values are bounded (Message-ID 160, From address 128 printable-ASCII characters; longer ones are omitted, making that copy ineligible), and the main function's cap for a blast-radius answer rises from 512 KB to 1.5 MB, above the schema's worst case of about 1.0 MB (tested), so a sender cannot make blast radius unavailable by inflating the answer. `parseRetryAfter` and credential loading moved to leaf modules (`retry.after.ts`, `certificate.loader.ts`) so the write broker's bundle contains no `GraphClient`.
  - Metrics `CampaignMessagesRemoved`, `CampaignRemovalErrors`, `CampaignRemovalRefused` (`Reason`), `CampaignRemovalNotAttempted`; `GraphBrokerCalls` with `Operation=remove_messages`.
  - SAM: `GraphWriteClientId`, `GraphWriteCertificateSecretArn` (both required together; must differ from the read app's), `GraphWriteEnabled` (default `false`), `GraphWriteAllowedMailboxIds`, `GraphWriteBrokerReservedConcurrency` (default 2), `CampaignRemovalMode` (default `dry_run`). Only with the write parameters: `GraphWriteBrokerFunction` (outside the VPC, no trigger, 256 MB, 100 s), its own role (its log group and the write secret only) and log group (365 days). Only with `CampaignRemovalMode=live` and campaign response: the main function's removal settings and `lambda:InvokeFunction` on the write broker. A stack that sets none of them is unchanged. `npm run package` builds `graph-write-broker.zip`; `npm run deploy -- … --write-broker <name>`.
  - Docs: `docs/ARCHITECTURE.md` "The mailbox write tier" (replacing the seam description, with the anchor and eligibility rules and a threat model that states the residual risk), `docs/CONFIGURATION.md` (keys, separate app registration, `Mail.ReadWrite`, certificate, optional Exchange application RBAC scoping, a staged rollout, who may invoke the write broker, customer-managed KMS keys, deploy order), `AWS.md`.
- **Outlook Report-button intake** (`PHISHY_REPORT_BUTTON_ENABLED`, SAM `ReportButtonEnabled`): Report-button submissions delivered by Microsoft 365's user-reported settings are handled silently, never emailing the reporter. Phishing reports are analyzed, stored and counted toward campaigns, and the security team is told only for malicious or suspicious verdicts or a failed analysis; junk / not-junk reports are counted and skipped. The reported email's subject replaces the wrapper's; the wrapper's header-dump body is discarded. Metric `UserReports` (`ReportedAs`).
- **Static attachment analysis** (`attachments.analysis.enabled` / `PHISHY_ATTACHMENT_ANALYSIS_ENABLED`, SAM `AttachmentAnalysisEnabled`): Phishy inspects attachment bytes itself, in process, never executing, rendering or fetching anything, with no new dependency (`src/services/attachments/`).
  - Real type from the bytes, name tricks (double extension, bidi override, padding, an extension Windows runs, type contradictions), and per format: HTML/SVG forms, password fields, scripts, redirects, smuggling markers; PDF JavaScript, actions, embedded files, links, text and the "almost no text but links" lure; OOXML macros, remote templates, external relationships, DDE, text; legacy OLE macro storages and embedded objects; RTF objects; zip/gzip/tar listings with nested archives, executables and overlap bombs; attached emails one level down; image dimensions; executables and installers marked high-risk and never parsed.
  - Facts under VERIFIED; extracted text in a new `attachment-content-{nonce}` CLAIMED fence, bounded with equal shares, head and tail, every cut disclosed. A per-email time budget (10 s) and decompression budget (64 MiB, 16 MiB per entry); failures become a status, never a failed analysis.
  - Risk fusion acts on two decisive findings only (a password form posting to a web host, an executable disguised as a document): a reason, a floor of 60, benign becomes suspicious. Nothing an inspection finds lowers risk. URLs in attachments feed IOC extraction (`url_in_attachment`, `attachment_url_domain`). With the flag off, parsing and prompts are unchanged. Limits `PHISHY_ATTACHMENT_ANALYSIS_TIME_BUDGET_MS`, `_MAX_BYTES`, `_MAX_UNCOMPRESSED_BYTES`, `_MAX_ARCHIVE_ENTRIES`, `_MAX_DEPTH`, `_MAX_TEXT_PER_ATTACHMENT`, `_MAX_TEXT_TOTAL`. Design notes on fetching original attachments and on model vision in `docs/ARCHITECTURE.md`.
- **Compromised-sender signals**: facts (no new risk floor) for a known supplier's real mailbox sending a short RFQ with a file link to its whole address book.
  - More link-protection wrappers: Barracuda Link Protection and Symantec / Broadcom Click-time URL Protection unwrapped; Mimecast URL Protect and Cisco Secure Email recognized and disclosed as hiding the destination. Targets accepted only as bounded absolute http(s) URLs; up to 4 nested layers. Sophos and Trend Micro time-of-click links are deliberately not unwrapped (their formats are not vendor-documented). IOC extraction stores the destination, not the wrapper.
  - File-share facts (`src/utils/file-share.ts`) for SharePoint / OneDrive, Google Drive, Dropbox, Box, WeTransfer, Egnyte, ShareFile, MEGA and iCloud Drive links, with whether the share appears to belong to the claimed sender.
  - Addressing facts (new VERIFIED `ADDRESSING` section, `src/utils/addressing.ts`): a Bcc blast to the sender's own address, a diverting Reply-To, a different Reply-To display name, the reporter not among the visible recipients. Link text that looks like a document file name on a link that is not a direct download from the claimed sender's domain is flagged. The parser keeps a forwarded original's `Cc` and every `To` recipient.
- **Checklist scoring** (experimental; `scoring.mode: checklist` / `PHISHY_SCORING_MODE=checklist`; the default `model` leaves the prompt and every score unchanged, pinned by a prompt-hash test). ### Fixed

- **An incident update is sent at once when a live removal first becomes possible.** On a deployment that removes live, the report that gives an incident its anchor (the reported email confirmed in the reporter's own mailbox) no longer waits out `updateIntervalMinutes`: the update carrying the live removal proposal goes immediately, and says why. - **The incident email counts people, not reports.** "3 people have reported" for three reports from two people now reads "2 people have reported the same … email (3 reports in all)"; the employee warning's "N colleagues reported this email" uses the same count of people.

- **The removal dry run's reply says what a removal would actually do.** It headlined every approved copy as "would remove", copies already in Deleted Items included; it now headlines the copies a removal would move to Deleted Items (inbox unread, inbox read, Junk, other or unidentified folder) and reports those already in Deleted Items apart, as left where they are. - **Decimal settings can be set by environment variable.** Only whole numbers were converted, so `PHISHY_GRAPH_SENDER_HISTORY_FANOUT_MULTIPLIER=2.5` (or a fractional `PHISHY_CAMPAIGN_RESPONSE_APPROVAL_TTL_HOURS` / `PHISHY_CAMPAIGN_CACHE_TTL_HOURS`) failed validation. - **Adversarial bounding**: body truncation is head+tail (padding can no longer push the payload out of view) and the link budget is filled round-robin across registrable domains (50 benign links can no longer crowd out the payload link). Every elision is disclosed to the model as a labeled fact

Tools are offered only when their backing data exists; the loop is capped at `PHISHY_AGENTIC_MAX_TOOL_ROUNDS` and any failure falls back to the standard single-shot analysis. Tool usage and accumulated token counts are recorded with each analysis
- AI interpretation of free-text email commands: with agentic mode on, security-team replies the keyword parser can't read are classified by the model, strictly constrained to the two known verdicts
- `converse()` on both AI providers: multi-turn, tool-capable conversations in the shared Messages format (Bedrock InvokeModel and the Anthropic API)
- Campaign verdict cache (`PHISHY_CAMPAIGN_CACHE_ENABLED`): when a flood of the same email is reported, the first report gets a full AI analysis and subsequent same-campaign reports reuse its verdict (migration 003) — consistent answers for every reporter, no duplicate AI spend. A security-team reply to any one report ("confirmed phishing" / "false positive") overrides the AI verdict for the whole campaign, and verdict feedback now adjusts indicators campaign-wide. Cache hits emit `CampaignCacheHits` / `EstimatedCostSavedUSD` metrics
- CloudWatch cost/usage metrics via Embedded Metric Format: every analysis emits tokens, estimated USD cost, latency, and verdict to the `Phishy` namespace, with no database or extra IAM required (`PHISHY_DISABLE_METRICS` to opt out)
- Per-model pricing table for cost estimation, replacing hardcoded Sonnet rates; includes the 10% Bedrock regional-endpoint premium
- Token usage capture for the Anthropic API provider (previously Bedrock-only)

### Changed
- **The analysis is no longer armed with attacker-controlled "facts"**: the forwarded sender's identity (parsed from the attacker-controlled body in inline forwards) moved from the VERIFIED block to a CLAIMED cannot-be-authenticated section; "legitimate systems" lists are reframed as the brands attackers impersonate most, not an allowlist; reasoning rules added — a familiar-looking From is not verification, and content that cannot be inspected is never "legitimate"
- **Default model upgraded to Claude Opus 4.8** on both providers (`claude-opus-4-8` / `global.anthropic.claude-opus-4-8`); model catalogs refreshed with Opus 4.6, Sonnet 4.6, and current Bedrock `global.`/regional ID formats
- Full-prompt logging in the Bedrock provider moved from info to debug level — reported email content no longer lands in CloudWatch logs at default log levels
- **License changed from GPL-3.0 to Apache-2.0**
- Bedrock model defaults and configuration updated for inference profiles and VPC endpoints

### Fixed
- **Security**: the pinned RDS CA could be silently bypassed for connection strings in libpq `key=value` form — `pg` gives an embedded `sslmode` precedence over `config.ssl`, and `sslmode=disable`/`no-verify` would fail open (connect with no TLS verification, no error). `sslmode`/`ssl` are now stripped from both the URL and key=value forms before the CA is pinned
- Risk fusion: a security-team ruling now overrides the **verdict** too, so the stored verdict and the employee report banner can't contradict the human ruling (a confirmation no longer leaves a `legitimate` verdict at critical risk; a clearance forces `legitimate`). A confirmed ruling preserves an already-malicious model verdict (e.g. `bec`)
- IOC dedupe lowercased entire URL values, which could merge two distinct malicious URLs (paths/queries are case-sensitive) and drop an indicator; only the scheme+host are now case-folded
- Tests no longer reference a real organization domain (CLAUDE.md requires invented `example.com`-style data only)
- Bedrock default model ID corrected to `global.anthropic.claude-opus-4-8`: on-demand invocation requires an inference-profile ID, and Bedrock rejects the bare `anthropic.claude-opus-4-8` form with a ValidationException (verified against a live account)
- **Security**: `X-Forwarded-For` was trusted verbatim as the report recipient — an attacker-influenceable header (often an IP chain, never validated) could redirect analysis reports. It now requires an extractable address on a safe domain, the same bar as every other source
- Outlook-style forwarded headers never captured the original subject: the marker pattern stopped at the literal `Subject:` before its value
- Messages whose content could not be retrieved from S3 still reported a guessed `s3Reference`/`s3Location`, misleading cleanup and provenance; they now report none
- External event payloads (API Gateway paths) were blind-cast instead of validated; malformed entries are now dropped with a warning
- Anthropic provider model catalog contained invalid IDs (wrong date suffixes) that returned 404 from the API; catalog rebuilt with current model aliases
- Cost estimation previously used hardcoded Sonnet 4.5 rates regardless of which model ran
- Security fixes from audit: XSS in reports, ReDoS in extraction regexes, SSRF in webhook URLs, error detail disclosure, prompt injection hardening
- Documentation listed environment variables the code never read: `BEDROCK_REGION` → `PHISHY_BEDROCK_REGION`, `BEDROCK_MODEL_ID` → `PHISHY_BEDROCK_MODEL`, `DELETE_AFTER_PROCESSING` → `DELETE_EMAILS_AFTER_PROCESSING`
- Base64 MIME decoding for forwarded content
- Bedrock VPC endpoint HTTP/2 stream timeout
- Config validation no longer requires an Anthropic API key when using Bedrock
- The built-in default config still pointed Bedrock at the retired Sonnet 4.5 dated model ID, overriding the schema's Opus 4.8 default
- Migration 002's `source` column default (`'report_link'`) violated its own CHECK constraint — leftover from the removed one-click feedback design
